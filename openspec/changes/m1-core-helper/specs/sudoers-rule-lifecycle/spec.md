# Sudoers Rule Lifecycle Specification

## Purpose

Defines the exact on-disk format, atomic creation, safe removal, and concurrency serialization of the NOPASSWD rule file `/etc/sudoers.d/90-nopass-<uid>`. This is the highest-risk surface in the system: every requirement here exists to guarantee `/etc/sudoers` and `sudo` are never left in a broken or ambiguous state. (PRD RF-04, RF-05)

## Requirements

### Requirement: Rule File Naming and Content Format

The system MUST write NOPASSWD grants only to `/etc/sudoers.d/90-nopass-<uid>`, never to `/etc/sudoers`. The content MUST consist of a fixed three-line comment header (`# Generated by NoPass — do not edit manually`, `# nopass-user: <sanitized-username>`, `# nopass-expires: <never|reboot|<epoch>>`) followed by exactly one `#<uid> ALL=(ALL) NOPASSWD: ALL` line using sudoers' numeric-UID syntax. The username interpolated into the comment MUST be sanitized to `[A-Za-z0-9._-]`; no other free text is interpolated anywhere in the file. The banner is a data contract, not interface text: it MUST NOT be localized, translated, or varied by locale under any circumstance, because `is_nopass_owned` anchors ownership detection on it and both rule removal and the boot sweep depend on that decision. Application i18n MUST NOT reach this file. (RF-04)

#### Scenario: Template renders the fixed format
- GIVEN uid 1000, username `jorge`, expiry `At(1789000000)`
- WHEN the rule is rendered
- THEN the output matches the fixed header and `#1000 ALL=(ALL) NOPASSWD: ALL` exactly
- Testable via: `cargo test` (`nopass-core::template`)

#### Scenario: Username with `.` is preserved, disallowed characters are stripped
- GIVEN username `ana.perez` and, separately, a username containing a space
- WHEN the rule is rendered
- THEN `ana.perez` appears verbatim in the comment; the space-containing name is sanitized to only `[A-Za-z0-9._-]` characters before interpolation
- Testable via: `cargo test`

### Requirement: Atomic Rule Creation

The system MUST create the rule file atomically: open the temp path (containing a leading `.`, e.g. `/etc/sudoers.d/.90-nopass-<uid>.tmp`) with `O_EXCL|O_CREAT|O_WRONLY`, mode `0440`, owner `root:root`; write content; `fsync`; validate with `/usr/sbin/visudo -cf <tmp>`; rename atomically to the final path only on success. On validation or rename failure, the temp file MUST be unlinked and no other state changed.

#### Scenario: Successful atomic write
- GIVEN no existing rule for the target uid
- WHEN `enable` runs
- THEN the temp file is created with `O_EXCL`, mode `0440`, is `fsync`ed, `visudo -cf` passes, and the file is renamed to the final path
- Testable via: root-only container test

#### Scenario: `visudo -cf` rejects a corrupted candidate
- GIVEN the rendered content is deliberately malformed
- WHEN `enable` attempts to write it
- THEN the helper exits 14, the temp file is unlinked, no rename occurs, and `sudo` remains functional
- Testable via: `cargo test` (exact `visudo` argv via `CommandRunner`) and root-only container test (real `visudo`)

#### Scenario: Rename fails after successful validation
- GIVEN `visudo -cf` succeeded on the temp file
- WHEN the rename to the final path fails (filesystem error)
- THEN the temp file is unlinked, the helper exits 16, and any prior rule file is left untouched
- Testable via: root-only container test

#### Scenario: Concurrent enable requests serialize instead of corrupting the file
- GIVEN one `enable` invocation is mid-write and holds the lock
- WHEN a second `enable` for the same or a different uid starts
- THEN the second call blocks on the flock until the first completes, then proceeds against a consistent file state
- Testable via: root-only container test

### Requirement: Rule Removal

The system MUST remove only rule files it created, identified by both the `90-nopass-<uid>` name pattern and the presence of the NoPass header comment. `disable` MUST succeed even when the file was already removed externally, treating absence as already-disabled rather than an error.

#### Scenario: Disable removes an existing rule
- GIVEN an active rule file for uid 1000
- WHEN `disable` runs
- THEN the rule file is deleted, any expiry timer for uid 1000 is stopped, and the state file is updated to inactive
- Testable via: root-only container test

#### Scenario: Rule file externally deleted before disable runs
- GIVEN the rule file for uid 1000 was deleted from a terminal before `disable` is invoked
- WHEN `disable` runs
- THEN the helper exits 0, updates the state file to inactive, and reports no error
- Testable via: `cargo test` (stubbed `CommandRunner`/statefile)

### Requirement: Mutation Serialization

Every mutating operation (`enable`, `disable`, `expire`) MUST hold an exclusive `flock` on `/run/nopass/lock` for its entire duration, released on completion or process exit.

#### Scenario: Sequential operations each acquire and release the lock
- GIVEN two sequential `enable`/`disable` calls
- WHEN each runs to completion
- THEN each acquires the lock at start and releases it at exit, with no overlap required
- Testable via: `cargo test` (lock abstraction)

#### Scenario: Lock already held rejects the caller
- GIVEN another process holds the flock on `/run/nopass/lock`
- WHEN a new mutating operation starts
- THEN it exits 15 (lock busy) without touching `/etc/sudoers.d/`
- Testable via: root-only container test (flock held by a separate process)
